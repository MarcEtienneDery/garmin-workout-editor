# AGENT.md

Guidance for AI coding agents working in this repository. `CLAUDE.md` has the Claude-specific version; this file is the tool-agnostic summary.

## Commands

```bash
npm install
npm run build          # tsc -> dist/
npm test               # Jest, single worker (required)
npx jest src/__tests__/mcpServer.test.ts   # one file
npx jest -t "name"                         # by test name
```

No linter; TypeScript strict mode is the gate. Run `npx tsc --noEmit` and the relevant tests before committing. (On Node 24.22.1 the TypeScript binder can crash with a segfault, with `tsc` and with `ts-jest`'s type check alike; Node 24.13.0 type-checks fine, and a transpile-only ts-jest config (`isolatedModules`, `diagnostics: false`) runs the tests.)

## Garmin rules

- Weeks run Monday to Sunday in UTC; schedule dates are ISO `YYYY-MM-DD`.
- Use `normalizeActivityType()` from `src/mocks.setup.ts` for activity types.
- Weights: activity sets use `maxWeight / 453.6` (grams to lbs); workout steps convert grams to lbs unless the unit is already `pound`.
- Open-ended steps use `endCondition: "lap.button"` with `endConditionValue: 0`.
- Keep the pause between detail calls (`GARMIN_DETAIL_GAP_MS`, 500 ms by default) in the activity sync and the `setTimeout` delays in the workout detail loops; they are rate limiting.

## MCP server

- Plan tools: `list_plans`, `read_plan`, `write_plan`, `upsert_plan_workout`, `validate_plan`, `list_exercise_names`, `unarchive_plan` (`list_plans` marks an archived plan with `archived: true`; `archive_plan` is below, since it changes Garmin). They take a logical `path` (`workout-plans/<name>.json` or `data/<profile>/<name>.json`); prefer `upsert_plan_workout` over `write_plan` for single changes. A plan `write_plan` (or `export_workouts` with an `outputPath`) creates under `workout-plans/` belongs to the `profile` argument, else the default or only profile (`dataProfile`; several profiles and none named is an error), so other profiles do not see it; an existing plan keeps its owner (`owner` of `PutOptions` is only read when the document is new). The web editor does the same: a profile login owns what it creates, the admin creates shared plans.
- Tools that change the Garmin account (`upload_workouts`, `upload_single_workout`, `schedule_plan`, `upload_and_schedule_plan`, `archive_plan`, `create_workout`, `schedule_workout`, `send_to_device`) need the user's explicit confirmation, after `validate_plan` has been shown (for `create_workout`, its `dryRun`).
- Uploads delete and recreate workouts that have a `workoutId` and write the new ids back into the plan.
- `create_workout` and `schedule_workout` work on one workout with no plan file (`createWorkout` and `scheduleWorkout` in `src/mcp/tools/garmin.ts`; the workout schema is `newWorkoutSchema` in `plans.ts`, strict, so a plan-only field such as `scheduledDate` is refused rather than ignored). `create_workout` never replaces: it passes on only the name, type, description and steps, so no `workoutId` can reach the upload that would delete it. `schedule_workout` (`WorkoutEditor.scheduleWorkout`) throws for a workout Garmin does not have, where `schedule_plan` skips it, and checks the date against the calendar (`new Date("2026-02-30")` is March 2, so the plan flow's `isNaN` check does not catch it).
- When adding or renaming a tool, update `src/__tests__/mcpServer.test.ts`, the server instructions in `src/mcp/createServer.ts` and the README table.

## Deployment

The MCP server runs in Docker on the NAS as `garmin-mcp`, defined in `~/docker/garmin.yml`; the plan editor runs beside it as `garmin-web` (same image, `node dist/web/server.js`, needs `WEB_AUTH_TOKEN` for the admin login (a profile can have its own sign-in password, set in Settings; the page has a sign-in form and sessions live in memory); nothing is mounted but `/data`, the old `/config` is only needed for one run of `import-env`). It builds from `/home/medery/git/garmin-workout-editor`; the database lives in `~/docker/garmin-mcp/data/garmin.db` (`sqlite_backup` it in `~/docker/backup.sh`). To deploy `main`:

```bash
git -C /home/medery/git/garmin-workout-editor fetch origin && git -C /home/medery/git/garmin-workout-editor merge --ff-only origin/main
cd ~/docker && docker compose -f garmin.yml up -d --build
docker logs --tail 5 garmin-mcp   # expect "listening on http://0.0.0.0:8787/mcp/<token>"
```

Reconnect MCP clients afterwards so they pick up tool changes.

Live settings are in the two `env_file`s, not in the repo's compose: `CREDENTIALS_KEY` (the **same** value in `./garmin-mcp/.env` and `./garmin-mcp/web.env`; it encrypts the saved Garmin and Renpho passwords, so a lost or changed key means entering them again in Settings) and, in `web.env` only, `TRUST_PROXY=cloudflare` (the web editor is reached through the Cloudflare tunnel, so without it every visitor shares one wrong-password limit and a stranger can lock the sign-in out).

### Dev environment

`scripts/dev-deploy.sh [--keep-logins] [source-dir]` (compose file `docker-compose.dev.yml`) deploys a second stack, `garmin-dev-web` (port 8798) and `garmin-dev-mcp` (127.0.0.1:8797), built from `source-dir` (default: the checkout the script is in, uncommitted changes included) into the image `garmin-workout-editor-mcp:dev`. Every run stops dev, takes a fresh `sqlite3 .backup` of the live database (live is only read), and replaces dev's copy, so dev edits do not survive a deploy. Its state is in `~/garmin-dev` (outside `~/docker`, so `backup.sh` skips it): `data/garmin.db`, and `tokens.env` with dev's own `MCP_AUTH_TOKEN` and `WEB_AUTH_TOKEN` (made once, never live's). `scripts/dev-deploy.sh down` stops it.

- The copy is scrubbed: the Garmin and Renpho logins (`credentials`), the Garmin tokens and the Renpho auto switches are removed, so dev behaves like a profile without Garmin and cannot change the real account (an upload from dev would delete and recreate the live workouts that share its `workoutId`s). `--keep-logins` keeps them.
- The Claude login for the Food view's AI box (`FOOD_AI_*`, `CLAUDE_CODE_OAUTH_TOKEN`) is copied from live's `web.env` on each deploy, so dev estimates draw from the same plan.
- Both services join the `cloudflare-tunnel` network as `dev-web` and `dev-mcp`, never `garmin-web`/`garmin-mcp` (that alias would make the tunnel answer from either container). To reach dev over HTTPS (the barcode camera needs it), add a public hostname in the Cloudflare dashboard pointing at `http://dev-web:8788`.

## Git

Work on a feature branch, never commit straight to `main`, and don't push or deploy without the user's go-ahead.
