# AGENT.md

Guidance for AI coding agents working in this repository. `CLAUDE.md` has the Claude-specific version; this file is the tool-agnostic summary.

## Commands

```bash
npm install
npm run build          # tsc -> dist/
npm test               # Jest, single worker (required)
npx jest src/__tests__/mcpServer.test.ts   # one file
npx jest -t "name"                         # by test name
```

No linter; TypeScript strict mode is the gate. Run `npx tsc --noEmit` and the relevant tests before committing.

On phones the strip of views scrolls rather than squeezing its labels |
| Food log | stored in the `nutrition` table of `garmin.db` (`src/shared/store/nutrition.ts`: one row per food with its day, meal, name, kcal and protein, carbs, fat in grams; `source` is `web` or `mcp`). Garmin has no place to store food (`consumedKilocalories` is read-only, from MyFitnessPal), so nothing is sent to it and no Garmin login is needed. The nutrients beyond the macros (fiber, sugars, saturated and trans fat, cholesterol, sodium, potassium, calcium, iron) are `src/shared/nutrients.ts`: one list that drives the checks (`parseNutrients`), the sums (`nutrientTotals`, `{ amount, foods }` per nutrient, so a total says how many foods state it), the Open Food Facts fields (`off`, read in `foodSearch.ts` `nutrientsOf`: every `_100g` value is in grams, milligrams are ×1000, sodium falls back to salt × 0.4, one out-of-range nutrient is dropped alone) and the MCP inputs (`nutrientsArg` in `mcp/tools/nutrition.ts`); `nutritionModel.js` mirrors the list and a test keeps them equal. They are one JSON `extras` TEXT column of `nutrition`, NULL for none, added by `migrateNutrition` inside the transaction that creates the schema (so the two processes opening one file together cannot both add it). **Unknown is never zero**: a key is absent when not stated, `changeFood` sets a key it is given, keeps one it is not and removes one given as `null`, and `parseDraft(draft, true)` sends an emptied field as `null`. A `Food` has `complete`: a barcode lookup does, a search hit does not (the search index holds fiber, sugars, saturated fat and sodium only), so `pickFood` fetches the product page and the picker's Add waits for it; a food kept in `food_cache` before the nutrients existed has no `nutrients` and is asked for again (the kept one is the answer when Open Food Facts cannot be reached). The rules (checking a food, kcal worked out as 4P+4C+9F when left out, totals per meal and day, the days of a range next to Garmin's burn from `wellness.totalKcal`, the average of logged days that are over) are `src/shared/nutrition.ts`; the MCP tools `log_meal`, `get_nutrition`, `update_meal_entry`, `delete_meal_entry` are `src/mcp/tools/nutrition.ts` (they act on `dataProfile()`, which reads no login) and the web routes `GET` and `POST /api/nutrition` call the same functions. A day with nothing logged is not a day of zero. Foods are found in the Food view by name or by barcode on Open Food Facts: `src/shared/foodSearch.ts` (server side, injected `fetch`, per-100 g `Food`, bad data dropped, `searchFoods` asks the index for `countries_tags:"en:canada"` first and appends a plain search only when fewer than `MIN_CANADIAN` (10) usable Canadian foods come back, `Food.canada` says which are which and the page headings the two groups; `plainWords` strips the query syntax (an unbalanced bracket or the word AND made the index ignore the Canada filter), scanned products kept in `food_cache`, `src/shared/store/foods.ts`; routes `GET /api/foods/search` and `/api/foods/barcode`), the quantity maths is in `nutritionModel.js` (`portion`, `scale`; the log gets the scaled numbers, so the schema did not change) and the camera is `public/barcodeScanner.js` (BarcodeDetector, else ZXing from `node_modules/@zxing/library/umd` served at `/vendor/zxing/`; ZXing is fetched and run without `define`, `exports` and `module` because the page's AMD loader would otherwise swallow it; `decodeFrame` is tested with `src/__tests__/barcodeScanner.test.ts`). The camera needs HTTPS. The Food view is `public/nutritionModel.js` (tested by `src/__tests__/nutritionModel.test.ts`) glued in `index.html`. **The AI box** estimates a meal from words and photos with Claude: `POST /api/foods/ai` logs nothing, the page shows the rows to check and logs them with `POST /api/nutrition` (`addFoods` lets each item name its own meal, so a multi-meal estimate is one atomic call). `src/shared/foodAi.ts` asks Claude one of two ways (`FOOD_AI_BACKEND`, `backendOf`): `api` is the Anthropic SDK's `messages.create` with `output_config.format` (a JSON Schema built from `NUTRIENTS`; never a forced `tool_choice`, which Sonnet 5.5 and Opus 5.5 reject with a 400) and `effort: "low"`, paid from API credit (`ANTHROPIC_API_KEY`); `cli` is `src/shared/foodAiCli.ts`, Claude Code's `claude -p` on a Claude plan (Pro, Max) with the same prompt and schema: `--input-format` and `--output-format stream-json`, `--json-schema`, `--tools ""`, `--restricted`, `--strict-mcp-config`, one user message that holds the photos as image blocks, and the answer is the `structured_output` of the `result` event; never `--bare`, which ignores the plan login. The child gets an allowlisted environment without `ANTHROPIC_API_KEY` (Claude Code would prefer it to the plan, and bill it); its login in the container is `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`; at most 2 run at once. The Dockerfile pins the Claude Code version because its flags are the contract: after changing it, run a real estimate by hand. Both answers go through the same checks: every food goes through `parseFood`, so one the log would refuse refuses the whole estimate; photos are checked (type, base64, size, magic bytes) and never stored; `FOOD_AI_MODEL` (default `claude-sonnet-5-5`) and `FOOD_AI_DAILY_LIMIT` (default 30, per profile and day, in memory; a call that failed is not counted; one estimate at a time per profile); neither the SDK's nor Claude Code's own messages reach the page (`failure()` and `failureOf()` word them, the class and status go to `console.error`). `public/foodPhoto.js` shrinks a photo to 1568 px and encodes it again as JPEG in the browser (EXIF and GPS dropped; `fitWithin` is tested by `src/__tests__/foodPhoto.test.ts`). The `ai*` functions of `nutritionModel.js` make the estimate's amount eaten a per-100 `Food` (`aiFood`), so the grams box and the `product` kept with the logged entry work as for a scanned food (a food whose numbers cannot be per 100 g is a fixed row, logged without a product); `AI_LIMITS` equals the limits of `foodAi.ts` and a test keeps them equal. `#food/ai` is the Food view with the box open, the address to bookmark: `startSub`, `urlOfView` and `showAi` in `index.html` keep `/ai` in the address while the box is open (`replaceState`, no history entries). Tests: `src/__tests__/foodAi.test.ts` (a fake client and a fake runner), `src/__tests__/foodAiCli.test.ts` (the flags, the environment, the result events, and a fake `claude` program started for real), the "estimating food with AI" tests of `webServer.test.ts`. The tests never call Claude (fakes stand in); after changing the prompt, the schema or the Claude Code version, check a real estimate by hand (the `cli` backend needs only a logged-in `claude`) |

## Garmin rules

- Weeks run Monday to Sunday in UTC; schedule dates are ISO `YYYY-MM-DD`.
- Use `normalizeActivityType()` from `src/mocks.setup.ts` for activity types.
- Weights: activity sets use `maxWeight / 453.6` (grams to lbs); workout steps convert grams to lbs unless the unit is already `pound`.
- Open-ended steps use `endCondition: "lap.button"` with `endConditionValue: 0`.
- Keep the pause between detail calls (`GARMIN_DETAIL_GAP_MS`, 500 ms by default) in the activity sync and the `setTimeout` delays in the workout detail loops; they are rate limiting.

## MCP server

- Plan tools: `list_plans`, `read_plan`, `write_plan`, `upsert_plan_workout`, `validate_plan`, `list_exercise_names`. They take a logical `path` (`workout-plans/<name>.json` or `data/<profile>/<name>.json`); prefer `upsert_plan_workout` over `write_plan` for single changes.
- Tools that change the Garmin account (`upload_workouts`, `upload_single_workout`, `schedule_plan`, `upload_and_schedule_plan`, `send_to_device`) need the user's explicit confirmation, after `validate_plan` has been shown.
- Uploads delete and recreate workouts that have a `workoutId` and write the new ids back into the plan.
- When adding or renaming a tool, update `src/__tests__/mcpServer.test.ts`, the server instructions in `src/mcp/createServer.ts` and the README table.

## Testing

- Web UI changes are not covered by Jest (the page is plain script in `src/web/public/index.html`): run `npm run web` and click through it, ideally also at phone width.
- Jest runs with `maxWorkers: 1`.
- Mock `@flow-js/garmin-connect`; use `getMockClient()` / `resetMockClient()` from `src/mocks.setup.ts`.

## Deployment

The MCP server runs in Docker on the NAS as `garmin-mcp`, defined in `~/docker/garmin.yml`; the plan editor runs beside it as `garmin-web` (same image, `node dist/web/server.js`, needs `WEB_AUTH_TOKEN` for the admin login (profiles can add `WEB_PASSWORD` to `.env.<profile>` for their own login; the page has a sign-in form and sessions live in memory), and `/config` mounted for its Garmin buttons). It builds from `/home/medery/git/garmin-workout-editor`; the database lives in `~/docker/garmin-mcp/data/garmin.db` (`sqlite_backup` it in `~/docker/backup.sh`). To deploy `main`:

```bash
git -C /home/medery/git/garmin-workout-editor fetch origin && git -C /home/medery/git/garmin-workout-editor merge --ff-only origin/main
cd ~/docker && docker compose -f garmin.yml up -d --build
docker logs --tail 5 garmin-mcp   # expect "listening on http://0.0.0.0:8787/mcp/<token>"
```

Reconnect MCP clients afterwards so they pick up tool changes.

## Git

Work on a feature branch, never commit straight to `main`, and don't push or deploy without the user's go-ahead.
